# Enhanced Codeforces Problem Dataset Features

Your scraped data likely contains fields like *title*, *statement*, *input/output format*, *tags*, *rating*, examples, etc. Beyond the obvious, here are additional dataset angles to consider (citing relevant sources where helpful):

- **Math/LaTeX content:** Count and classify all math expressions. Codeforces uses LaTeX (MathJax) for equations: inline math is delimited by `$…$` and display math by `$$…$$`. You can scan the raw HTML or Markdown for these markers (or `<script type='math/tex'>` tags). Older problems may render formulas as `<img>`s (see Codeforces tutorial: “older equations… rendered as images”). Extract metrics like **number of formulas**, **inline vs display count**, and even **complexity of commands** (e.g. presence of `\sum`, `\int`, `\frac`, matrices). For example, you could count how often summation notation (`\sum`) or fractions (`\frac`) appear, or how many multi-line displayed equations occur. These measures (math density, typical commands) can then be correlated with problem rating. As one idea: “Do harder problems (higher rating) use more complex math notation?”  

- **Problem structure patterns:** Identify structural features in each statement. For instance, note whether a **“Note:”** section appears (many problems have optional notes after examples). Detect if the problem is **interactive**: the problem text will mention an “interactor” or special judge (e.g. see CF’s statement templates). Record how many **sample tests** are given, and if multiple testcases are implied (look for phrases like “the first line contains *t*” and loops over *t*). Identify if a problem uses **file I/O** vs **standard I/O**. (The HuggingFace CF dataset includes an `input_mode` field, distinguishing “stdio” vs “file”.) You could also count the number of `<img>` tags or other media in the statement to flag problems with diagrams or formulas as images (older CF problems often had more images). Track these features over contest ranges (for example, older contests vs newer ones). You suggested “Average number of examples per rating tier”; more generally, you can compute statistics like average examples, notes, images per contest or rating.

- **Constraints and complexity cues:** Extract all numeric constraints from the text (e.g. “n ≤ 10^5”, “m ≤ 1000”). No public dataset seems to have done this systematically, so it would be novel. Once parsed, store each constraint (variable name and bound) as structured data. This enables queries like “find problems where n ≤ 10^5”. Moreover, constraint values often imply solution complexity. For example, CF authors note rules like “if n ≤ 10^5, expect an $O(n\log n)$ or $O(n)$ solution”. By analyzing your constraint data, you could cluster problems by complexity (e.g. small vs large $n$ suggests brute force vs optimized solution). Also collect the problem’s **time/memory limits** and see how they vary with rating or tag. All these give insight into the computational difficulty of problems.

- **Keyword hints / algorithmic cues:** Scan the statement text for **algorithmic keywords** that hint at the solution. The user examples already list “greedy, binary search, construct, permutation,” etc. You can extend this by searching for terms like “dp” or “dynamic”, “graph”, “tree”, “dfs”, “bfs”, “modulo”, “flow”, “geometry”, “probability”, “prime”, “matrices”, etc. Count how often each keyword appears in problems (versus their official tags). For example, you might find problems tagged *greedy* that never use the word “greedy” in the text. (In fact, one CF analysis heatmap highlights that topics like DP, graphs, greedy vary in frequency across ratings.) This can help build a dataset of “implicit tags” or check tag accuracy. Additionally, detect common phrases like “find the maximum/minimum,” “optimal,” or words like “construct,” “permutation” – these often hint at the underlying algorithmic theme.

- **Length and readability over time:** Compute metrics like **character or word count** of problem statements, notes, and examples. Plot how problem length has evolved by year or contest. Are newer problems shorter/longer on average? Similarly, measure **math density** (fraction of statement that is math) over time or rating. Check if contests from earlier years have more images or verbose storytelling (some older CF problems had lengthy descriptions). You could also quantify how often problem statements use complex sentence structures or rare words (e.g. via a readability index or unique word count). 

- **Tag and topic trends:** Beyond checking single tag accuracy, analyze tag usage patterns. For example, track tag frequency by year or contest type (Div.1 vs Div.3). Build a “tag co-occurrence” graph: which tags commonly appear together. Examine if certain tags correlate with others (e.g. problems tagged *dp* often also have *graphs*). Compare the official tags vs the text: e.g., how many *dp*-tagged problems explicitly mention “dp” or “dynamic programming”? This helps uncover cases where the tag set might be incomplete or misleading. You could also look at how often problems include category keywords (like “geometry” or “trees”) vs their actual tags, to gauge tag consistency.

- **Examples and I/O patterns:** Analyze the sample tests. Count how many example test cases each problem has. See if sample inputs cover edge cases (for instance, do they include max/min values of constraints). Determine if example outputs match edge-case formatting (e.g. “Impossible” cases, or special text). You could also parse the structure of inputs: how many lines, whether inputs form a matrix, graph (list of edges), or simple variables. Collect statistics like “average number of numbers in input” or detect if input mentions “multiple test cases.” If the scraped data includes an “interaction_format” or special judge, record those too.

- **Competition and contest metadata:** If you have contest info (contest ID, name, date), you can derive features like which **contests or rounds** tend to have more of certain tags or difficulty. For example, educational rounds vs grand prix rounds might differ in content. Compute how many problems per contest, or analyze time since contest (age) vs problem style. If scraped with contest names, note differences: ICPC vs CF tag usage. 

- **Miscellaneous novel angles:** Here are a few more ideas no one’s published:
  - **Formula complexity metrics:** Build a “complexity score” based on LaTeX: e.g. weight display equations by number of summed terms, integrals, or nested fractions.  
  - **Constraint correlation with time limits:** See if tight constraints (e.g. $n>10^7$) come with longer time limits (3s vs 1s).  
  - **Subtask/partial scores:** Some problems (especially older or mirrored ones) may have subtasks; detect any “subtask” keywords.  
  - **Example diversity:** Measure how varied the sample inputs are (e.g. distribution of small vs large cases in examples).  
  - **Language features:** If relevant, note if statements include non-standard characters (like HTML entities), or code blocks vs text blocks in problem statement.  
  - **Dataset validation:** Ensure your JSON schema captures all fields (title, statement, tags, examples, constraints, I/O mode, etc.) and flag any missing/empty entries. Cross-check that scraped tags match known Codeforces tag list (to catch typos or new tags).

Each of these features can be stored in your final JSON export. For instance, you might have fields like `num_formulas`, `has_note_section`, `is_interactive`, `num_examples`, `constraints: {n:100000, m:1000}`, `keyword_greedy_count`, etc. By enriching the dataset this way, you not only power your VS Code extension but also create a valuable resource for CF analytics and machine learning (none of which, to our knowledge, have been fully published yet).  

**References:** Codeforces uses MathJax for LaTeX (inline `$…$`, display `$$…$$`), and CF blog posts discuss inferring complexity from constraints and topic frequencies across ratings. The open CF problem dataset shows the kinds of fields you can extract (title, tags, rating, I/O mode, examples, editorial, etc.).
